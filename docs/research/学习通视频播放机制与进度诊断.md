# 学习通视频播放机制与进度诊断

> 研究日期：2026-09-25
>
> 范围：只读分析仓库代码、提交历史和可公开访问的脚本页面。本文不把第三方用户脚本或猜测当作学习通第一方协议。

## 结论摘要

1. **学习通任务完成与墙上经过的时间不是同一个量。** 当前脚本只控制 iframe 内的 `videojs` 播放器和页面提供的 `isUnFinishJob()`，没有自己实现或显式调用学习通的进度/心跳接口。服务端是否收到进度，必须看浏览器 Network 请求。
2. **“20 分钟视频现实播放 10 分钟”不能由截图中的一次 31 秒随机暂停解释。** 31 秒暂停最多造成约 31 秒墙钟损失；如果 17:46:21 到 19:38 期间视频进度只有约 5 分钟，优先怀疑播放器实际处于 paused/等待/缓冲状态、页面心跳或进度请求被拒绝/丢失，或平台按有效观看区间累计，而不是按墙钟累计。
3. **仓库脚本存在会放大问题的控制竞争。** 随机暂停定时器、每秒的 `isUnFinishJob()` 轮询、`videojs` 的 `ended` 事件和速率恢复都可能改变播放状态。当前工作区版本已增加 `startPlayback()`、播放速率恢复和 `randomPauseActive` 标记，但这些改动只能改善脚本侧行为，不能证明平台服务端进度上报正常。
4. **没有公开可验证的 ananas 第一方源码。** 公开检索得到 GreasyFork 脚本页面，但源码端点返回网页壳/验证脚本；grep.app 对 `isUnFinishJob`、`video_html5_api` 等关键词没有可用的第一方命中，后续请求还触发了 429。因此平台内部函数、心跳 URL、参数签名和判定阈值仍需用户提供 HAR 或现场 Network 日志确认。

## 本地代码证据

证据文件：[`scripts/userscript/学习通脚本.js`](../../scripts/userscript/学习通脚本.js)

### 播放器控制链路

- `2306`：`Cx.video(iframeWindow)` 等待 `#video_html5_api`。
- `2308`：通过 `iframeWindow.videojs("video_html5_api")` 获取播放器，并查找 `.vjs-big-play-button`。
- `2309-2314`：设置静音、初始 `playbackRate(1)`，监听 `ratechange`；当前版本在速率不是 1 时恢复到 1 倍。
- `2317-2324`：`startPlayback()` 调用 `player.play()`，并记录播放 Promise 的失败。
- `2328` 附近：随机暂停触发间隔为 30-93 秒，暂停后计划 2-5 秒恢复；这属于脚本行为，不是平台日志中的“暂停时间”本身。
- `2339-2340`：恢复随机暂停前调用 `isUnFinishJob()`，若平台页面认为任务已完成则不恢复。
- `2409-2415`：每秒检查 `isUnFinishJob()`；任务未完成且播放器 paused、`currentTime() < duration()` 时调用 `startPlayback()` 和大播放按钮。
- `2418`：监听 `ended` 事件并结束脚本等待。

这些代码**没有**出现 `fetch`、`XMLHttpRequest`、`GM_xmlhttpRequest` 或明确的进度上报 URL 来提交 `currentTime`。因此，进度/心跳请求很可能由学习通 iframe 自己的第一方脚本发出，或由 `videojs` 事件触发后在页面脚本中发出；当前仓库无法从静态代码证明其请求格式。

### 为什么“随机暂停”不是充分解释

脚本的随机暂停一次只暂停 2-5 秒；日志中的“触发间隔 31 秒”是**距离下一次触发的等待时间**，当前版本已将日志文字改为“触发间隔”以免误读。即使把 31 秒误当作暂停时长，也不足以解释约 90 分钟墙钟只积累约 5 分钟视频进度的比例差。

更可能的分层解释是：

1. 浏览器中的视频时间 `currentTime` 增长速度低于墙钟（暂停、缓冲、解码或页面不可见导致）。
2. 视频时间增长了，但平台进度请求没有成功到达或被服务端接受；页面的 `isUnFinishJob()` 仍返回未完成。
3. 请求到达，但服务端按有效观看区间、心跳间隔、时间戳或反作弊规则折算，导致服务端记录小于播放器表面进度。
4. 脚本的每秒恢复逻辑与页面自己的暂停/播放逻辑竞争，使播放器反复进入暂停或等待状态。

以上第 2、3 项不能靠当前仓库确认，必须查看现场请求和响应。

### 可用结果

- GreasyFork 页面能证明脚本项目存在并提供“Source code”页面，但本次 HTTP 响应包含网页壳和第三方验证脚本，未取得可引用的第一方 ananas 模块源码。
- grep.app 对 `isUnFinishJob` 没有可用命中；连续查询还收到 HTTP 429。不能据此证明平台没有该函数，只能说明公共索引没有提供可验证实现。
- 未发现学习通官方公开文档说明 `isUnFinishJob()`、视频进度接口、心跳间隔或完成阈值。

### 不能下的结论

- 不能仅凭函数名推断服务端接口 URL。
- 不能假定 `currentTime()` 等于服务端已确认的有效观看时长。
- 不能假定 `ended` 事件一定触发了学习通任务完成请求；当前脚本只是把它当作本地等待结束条件。
- 不能通过修改 `playbackRate` 或手动设置 `currentTime` 来证明平台会接受对应进度；这需要真实响应验证，并可能触发平台风控。

## 可操作的现场验证方案

以下步骤只做观测，不改请求、不重放请求、不上传账号数据。

### A. 记录播放器真实状态

在视频 iframe 的 DevTools Console 中，每秒记录一行：

```js
const v = document.querySelector('#video_html5_api');
setInterval(() => console.log({
  wall: Date.now(),
  currentTime: v?.currentTime,
  duration: v?.duration,
  paused: v?.paused,
  readyState: v?.readyState,
  networkState: v?.networkState,
  playbackRate: v?.playbackRate,
  ended: v?.ended,
}), 1000);
```

同时记录脚本日志中的“随机暂停触发/恢复”和浏览器的 `stalled`、`waiting`、`playing`、`pause`、`play` 事件。若 `currentTime` 本身只增长约 5 分钟，问题在播放/缓冲/暂停层；若 `currentTime` 增长接近 20 分钟而平台仍显示 5 分钟，问题在进度上报或服务端折算层。

### B. 捕获进度/心跳请求

1. DevTools -> Network，勾选 Preserve log 和 Disable cache。
2. 只过滤当前视频 iframe 所在域名，以及 `fetch`/`XHR`；不要把 Cookie、Authorization、token、完整课程 URL 分享到公共渠道。
3. 从视频开始到结束保存 HAR（可先在本地脱敏）。重点查找请求体/查询参数中含 `jobid`、`dtoken`、`objectId`、`duration`、`currentTime`、`playTime`、`playingTime`、`watchTime`、`enc`、`clazzId`、`courseId` 的请求。
4. 对每个候选请求记录：发送时间、请求方法、URL 路径（域名和查询中的 token 脱敏）、状态码、响应关键字段、相邻两次请求的时间间隔、进度值是否单调增加。
5. 对比播放器日志：请求发送时的 `currentTime`、服务端响应中的进度、页面任务状态变化（`isUnFinishJob()` 返回值）。

### C. 最小对照实验

使用同一视频、同一账号、同一浏览器配置，分两次：

1. 关闭用户脚本，只手动播放 3-5 分钟，记录播放器时间和进度请求。
2. 开启用户脚本但暂时关闭随机暂停逻辑，再播放相同长度，记录相同字段。

不要在实验中使用倍速、拖动进度条或批量并发。若关闭脚本后进度正常、开启脚本后播放器时间明显停滞，优先修脚本控制竞争；若两者播放器时间正常但服务端记录都偏低，优先检查平台请求响应和账号/课程侧限制。

## 对当前问题的优先级判断

| 优先级 | 假设 | 现有证据 | 需要的验证 |
| --- | --- | --- | --- |
| 高 | 实际视频处于 paused/waiting/buffering，墙钟继续走 | 脚本多处主动暂停/恢复；截图只记录一次随机暂停 | A 的 `currentTime`、`paused`、`readyState` 时间序列 |
| 高 | 页面进度/心跳请求失败、被拒绝或间隔异常 | 仓库没有显式上报实现，平台模块未公开 | B 的 HAR 状态码、响应字段和请求间隔 |
| 中 | 脚本轮询与页面自己的播放器控制竞争 | 每秒 `isUnFinishJob` 检查并可能调用 `play()`/点击大播放按钮 | 对照实验、事件日志、脚本版本差异 |
| 中 | 服务端按有效观看区间或反作弊规则折算 | 符合“播放器/墙钟/服务端三种时间”可能不同，但没有第一方阈值证据 | HAR 中请求进度与服务器响应、课程任务页最终值 |
| 低 | 单次 31 秒随机暂停造成全部差异 | 数量级不符；最多解释几十秒 | 无需优先投入 |

## 后续实现边界

在拿到脱敏 HAR 前，不应猜测并硬编码学习通进度接口，也不应通过伪造请求或强制跳转进度来“修复”完成判定。下一步最有价值的输入是：

- 一份只包含该视频会话的脱敏 HAR；
- A 实验生成的 1-2 分钟播放器状态日志；
- 视频 iframe 的实际 URL 路径（去掉查询参数中的 token）；
- 发生问题时 Network 中最后一次成功和第一次失败的进度请求状态码/响应字段。
